## The race, per alert

### #955 `corporate/store-lock.ts` · #811 `bus/claim.ts` — mutual exclusion, actually broken

Both acquire correctly: `openSync(p, "wx")` is `O_CREAT|O_EXCL`, an atomic test-and-set. Both
broke their own exclusion in **recovery**. On `EEXIST` they read the holder, judged it dead, and
`rmSync`/`unlinkSync`-ed the **path** — and a path resolves afresh on every call:

```
A: open wx -> EEXIST          B: open wx -> EEXIST
A: read -> owner S (dead)     B: read -> owner S (dead)
                              B: unlink(S); open wx -> B HOLDS THE LOCK
A: unlink(path)               <- DELETES B'S LIVE LOCK
A: open wx -> A HOLDS THE LOCK
```

Two runs interleaving one organization's store and both pushing; two agents claiming one backlog
item. `store-lock.ts`'s `release` had the same shape — read the owner, compare the pid, unlink
the path — so a run that outlived its own takeover could delete its **successor's** lock, which
is exactly what the pid comparison was written to prevent.

`claim.ts` already carried the honest diagnosis of why the two natural narrowings do not close
it (one descriptor for pid+mtime; a dev+ino compare before the unlink) and stopped one step
short of the conclusion. There is no `funlinkat`, so a path-based unlink of an object you did
not create cannot be made race-free — **therefore stop unlinking objects you did not create.**

**Fix — `src/Core.TypeScript/io/exclusive-lock.ts`.** A lock is a **directory**; a holder is
`<generation>.lock` created with `O_EXCL`; a stale generation is **superseded** by creating
`generation+1`, never deleted. Every unlink in the protocol targets a name exactly one process
could have created, performed by that process. GC of lower generations is unconditional (no
check precedes it) and has no correctness role — while our generation exists, every concurrent
scanner computes a maximum at least as high, so removing lower entries cannot change any
exclusion decision.

`store-lock.ts` additionally still **obeys** a live holder left by the old single-file protocol —
read-only, never deleted — so a run in flight across this change is not overrun.

### #256 `zflash/esp-inject.test.ts` · #259 `zflash/flash-and-inject.ts` — a checked re-open

A different shape: a deliberate fresh `open` used as the read-back assertion. Deleting the
re-open is **not** a fix — reusing the write handle proves only that the bytes this process wrote
are the bytes this process wrote, a check that cannot fail. What was missing is proof that the
two descriptors name the same object, so the re-resolution can no longer pass on the wrong one.

`src/Core.TypeScript/io/handle-identity.ts` answers in **three** registers — `same` /
`different` / `unknown` — because `fstat` on a raw device handle may report nothing, and reading
two zeroes as "same" would be the vacuity being removed.

**These two alerts are expected to stay OPEN.** The second `open` remains, by design; CodeQL is
right about the shape. What changed is that a swap is now a loud failure instead of a silent
pass.

## Alert #798 `actions/untrusted-checkout` — assessment, no gate.yml change

**Located.** The flagged region is `gate.yml:352-527` at commit `db350f8`: the `detect` step of
`path-filter` through the end of that job. The job's `actions/checkout` is **already pinned to
`base.sha`** (landed 2026-09-10, #17234). What CodeQL is reading as the untrusted checkout is
`detect`'s `git fetch --no-tags --depth=1 origin "$PR_BASE_SHA" "$PR_HEAD_SHA"`, which brings the
untrusted head **objects** onto disk, followed by code running later in the same job.

**Assessment: true about the shape, not exploitable as written.**

1. Trigger is `pull_request`, workflow permissions are `contents: read` — unprivileged.
2. `git fetch` writes to `.git` only. There is no `git checkout`, no `git merge`, no
   `git restore` — the **working tree is never switched to head**.
3. `git diff --name-only BASE HEAD` reads names, never content.
4. The only executable read from the tree — the domain classifier — runs from the **base**
   checkout, which the file already documents at line ~485.

So nothing from the PR head is ever executed. But, exactly as the existing comment at line ~336
says about the previous instance, that is a property of the *current* job held by nothing but
review: a future step that ran something out of the fetched objects would make it load-bearing.

**Proposed minimal patch — NOT applied.** Fetch into a scratch bare repository so untrusted
objects never enter the workspace's `.git` at all. Two-dot diff semantics are unchanged (it does
not walk ancestry), and the fail-closed property is unchanged (a missing object still exits 128
under `set -e`):

```bash
TMP="$(mktemp -d)"
git -C "$TMP" init --bare -q
git -C "$TMP" fetch --no-tags --depth=1 \
  "${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}" "${PR_BASE_SHA}" "${PR_HEAD_SHA}"
CHANGED=$(git -C "$TMP" diff --name-only "${PR_BASE_SHA}" "${PR_HEAD_SHA}")
```

**Why it is not in this PR, stated plainly rather than implied:** `path-filter` decides which
gate legs run, no local harness executes a workflow edit, and I would be shipping an unverified
change to the one job that gates everything else. An untested edit there is a worse trade than
an open MEDIUM alert on a non-exploitable shape. It belongs in its own PR where the gate run
itself is the test. **No ruleset or branch-protection change is proposed or made.**
