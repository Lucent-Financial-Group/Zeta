## What this is

The follow-up loop on agentic-tpm was not converging. Measured on !163/!164, 2026-09-12: **28 follow-up rounds pushed something in 15**. The other 13 produced nothing durable, at 5–41 min and $2–13 each. The account's usage limit that everyone noticed was the *symptom* — the loop had already burned the quota failing to converge.

Five separate failures were in the way. Each is fixed here, each with a test whose falsifier I ran.

## The fixes

**1. `--parallel` was inert.** The runtime queued both requests and recorded *"3 at a time"* — yet task-032's session began at `15:15:46`, the second task-040's ended. `ferry` was never at fault: it starts N workers with `Promise.all`, but the port beneath called **`spawnSync`**, which holds the only thread for as long as the session runs. No second worker could ever be scheduled.

Now an awaited `spawn` returning exactly what `spawnSync` returned, so no caller changed.

**2. Nobody tested the composition.** `ferry.test.ts` passed throughout — it is handed *async* work. `followup-commands.ts` had no test at all. Both halves looked right; the seam between them was never exercised. `followup-commands.test.ts` now tests it: with `spawnSync` the overlap measures **3117 ms** and fails, awaited it is **1830 ms** and passes.

**3. A proof was spent every round.** The reviewer proves each claimed item non-vacuous by hand — scratch worktree, production file reverted, test re-run — and was handed all twelve items every round, including ones it had already proved. One `implementation_review` on task-040: **42.6 min, 167 turns, $17.05**.

`itemsStillToProve` keeps the proof to what has not been proved and tells the reviewer what it may skip. Proved items stay **open** — their threads are still owed an answer.

**4. Three limit refusals parked a request for good.** The give-up count clears only on a follow-up that *ran*, and a parked request never starts one — a one-way door. An outage between 07:32Z and 13:52Z left 13 such refusals on each of two requests; hours later, on an account with quota, the watcher parked **both** ("a person is needed") with nothing wrong with either.

A limit stops a session *before* it starts. It is not the work failing, so it no longer counts. Matched on what the refusal says, so the outage already in the log reads correctly too.

**5. A limit looked like a crash.** It left by the same exit code, so the organization could not tell *"this agent failed"* from *"this agent was never allowed to start"*. It now leaves by its own code (`7`) carrying the reset it named.

**6. The review bot's announcement was treated as work.** *"Seen, … actively reviewing this merge request"* arrives as an ordinary note, not a GitLab system note — so it became an action item, and an action item is answered by a session. **Ten of the 28 rounds** went on that, and it returns with the next push. No longer ingested; matched narrowly on the phrase **and** a short body, so the same bot's actual review still is.
