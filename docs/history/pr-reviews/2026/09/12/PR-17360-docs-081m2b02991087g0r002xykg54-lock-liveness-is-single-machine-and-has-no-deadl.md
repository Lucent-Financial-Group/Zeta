## Description

Raised by Aaron on the `exclusive-lock` protocol in #17335:

> *"can this make you get stuck forever if the agent never releases the lock? should they have timeouts or something?"*
> *"also kill pid is assuming the agents are on the same machine, ours will often not be"*

Both true, and **one** defect rather than two. #17335 removed the *filesystem race* and deliberately did not touch the *failure detector* — the file says so itself: staleness is the caller's predicate, typically `kill(pid,0)`, which "does not turn pid liveness into a perfect failure detector."

### What the predicate cannot see

**A hung holder never ages out.** Alive but wedged — stalled network read, `SIGSTOP`, pathological retry — answers `kill(pid,0)` as alive, so the lock is obeyed indefinitely. A crash is handled; a hang is not, and there is no deadline anywhere in the protocol.

**A remote holder is judged by the local kernel.** `LockOwner` is `{ pid, startedAt }` with **no machine identity**, so the predicate cannot tell it is being asked about a foreign process.

| surface | lock path | cross-machine today? |
|---|---|---|
| `bus/claim.ts` | `BUS_DIR = /tmp/zeta-bus` | no — local by construction; the pid check matches its transport |
| `corporate/store-lock.ts` | `storeDir`, caller-supplied | **yes, already possible** — nothing stops two machines sharing one store |

So `claim` is latent; `store-lock` is exposed **now**, silently.

**It fails in the dangerous direction.** A remote holder's pid almost certainly isn't running on the observing machine → reads `DEAD` → takeover → two live writers. That is the same two-holders state #17335 just removed, reached by another route. The opposite error (recycled local pid reads `ALIVE`) merely wedges.

### Why a bare timeout is not the fix

It converts *stuck forever* into *silent double-write*: a deadline cannot establish that the old holder stopped, only that it hasn't been seen. A holder in a long GC pause wakes mid-write and interleaves. **Anchor:** Kleppmann, *How to do distributed locking* (2016).

### The shape that works

1. **Liveness the holder ASSERTS, not one the observer INFERS** — a renewed lease. Needs nothing about the holder's kernel, and ages out a hang.
2. **The generation IS a fencing token — make the resource check it.** It's already monotonic and already recorded; the resource must refuse a write carrying a generation below the highest it has seen. **This is the missing piece** — nothing downstream inspects it.
3. **Three-valued predicate.** A foreign pid is `unknown`, never `dead`, and unknown must not authorize takeover. Needs host + boot id on `LockOwner`.

### Cheap partial win, needing none of the above

`store-lock`'s owner already carries `startedAt`, so a caller can report *"held 3h by pid N since T"* instead of blocking silently — an invisible wedge becomes a visible one, with no correctness change.

### Falsifiers (both stated so neither fix can be believed without them)

- **Hang:** a holder alive and never releasing — the waiter must proceed **and** the hung holder's later write must be **refused**. A test where the waiter proceeds and the old write still lands is the double-write this row exists to prevent.
- **Cross-machine:** an owner naming a pid on another host — the predicate must return `unknown` and the takeover must **not** happen. This fails against current code, which is what makes it a falsifier rather than a description.

This PR files the row only; it changes no lock behaviour.
