## The hard part: "locally"

`.claude/rules/clone-at-tag-stays-sufficient.md` requires the tree to stay checkable from `git clone` at a tag with no package manager present. So there are two separated acts:

- `ace outdated` -- reads a committed snapshot. **Zero network.**
- `ace outdated --refresh` -- re-observes from the registries and rewrites `registry/latest-known/<ecosystem>.json`. The only networked path, never run implicitly.

## Staleness: "I do not know how current my knowledge is"

The snapshot is data in the repo, so it ages. Two **orthogonal axes**, never collapsed into one verdict:

```
DISTANCE   UpToDate | Behind | Ahead | Unknown
FRESHNESS  fresh | aging | stale | absent
```

Crossing them is the point. `UpToDate` + `stale` renders as **"current as of a stale observation"** and prints the age in days -- never a bare "current". A per-row `observedAt` means a partial refresh keeps honest per-row ages instead of laundering them all to today. The summary line always carries the unknown count and the age band, so exit 0 cannot read as "all current".

`Unknown` is the **default**. A row reaches `UpToDate` only by positively parsing both versions and comparing them. No snapshot entry, an unparsable version, a range pin -- each lands on `Unknown` **with a stated reason**. There is no code path from absence to "current".

## Exit codes

```
0  ran; nothing behind
1  ran; something behind          (--fail-on-unknown and --max-snapshot-age-days also land here)
2  could not run                  -- no manifest readable, or nothing known at all. NEVER a pass.
```

A test asserts total ignorance and all-current produce **different** exit codes.

## Finding 1 — `FSharp.Core` resolves to a different `contentHash` per platform (30 locks)

The 30 affected locks are **exactly** the 30 that reference `FSharp.Core`, and `net10.0/FSharp.Core` is the **only** differing entry in any of them. Same requested range, same resolved version `10.1.400`, three different hashes:

| leg | `contentHash` (truncated) |
|---|---|
| `macos-26`, `windows-2025`, **and the committed files** | `H9wlZ/tWgNp+Q4WQ5aUSi3XO…` |
| `ubuntu-24.04` | `mxCkXuBt4wyRMmHf4boZXm30…` |
| `ubuntu-24.04-arm` | `90c8OKU41fCkzphlHq8nQiOJ…` |

The committed locks are the **macOS/Windows** answer. Both Linux legs disagree — with the committed files *and with each other*. So `dotnet restore Zeta.sln --locked-mode` on the gate would fail `NU1403` on every Linux leg, which is most of the gate. Had this been widened on the strength of the static scan alone, it would have broken `main`.

### Mechanism — traced to the SDK line that causes it

This began as a hypothesis and was then found in the shipped SDK targets. `sdk/<version>/FSharp/Microsoft.FSharp.NetSdk.targets` adds the SDK's **own bundled copy** of `FSharp.Core` as an additional restore source for every F# project:

```xml
<PropertyGroup Condition=" '$(DisableImplicitLibraryPacksFolder)' != 'true' ">
  <RestoreAdditionalProjectSources Condition="Exists('$(_FSharpCoreLibraryPacksFolder)')">
    $(RestoreAdditionalProjectSources);$(_FSharpCoreLibraryPacksFolder)
  </RestoreAdditionalProjectSources>
</PropertyGroup>
```

`_FSharpCoreLibraryPacksFolder` is `sdk/<version>/FSharp/library-packs/`, holding exactly one file: `FSharp.Core.10.1.400.nupkg`, **built per SDK platform**. The nuget.org `.nupkg` sha512 (`aM8GRu3juiHLoQqcV7+nnynXrw1G…`) matches none of the three lock values, and the locally bundled copy hashes differently again (`T9R1BJRK32NxCH9vneBi…`) — the same story from the other side.

### It is not per-platform at all — it is NONDETERMINISTIC (measured, not inferred)

The lane ran a **second** time ([`34664982677`](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/34664982677)), ~30 minutes later, same commit, all five legs restoring. **`macos-26` produced a fourth value it had not produced before:**

| leg | run `34664278420` | run `34664982677` | |
|---|---|---|---|
| `macos-26` | `H9wlZ/tWgNp+Q4WQ5aUSi3XO…` | `C8Myl8/HMoTWw0K/xJ+Q6JHl…` | ⚠️ **changed between runs** |
| `ubuntu-24.04` | `mxCkXuBt4wyRMmHf4boZXm30…` | `mxCkXuBt4wyRMmHf4boZXm30…` | stable |
| `ubuntu-24.04-arm` | `90c8OKU41fCkzphlHq8nQiOJ…` | `90c8OKU41fCkzphlHq8nQiOJ…` | stable |
| `windows-2025` | `H9wlZ/tWgNp+Q4WQ5aUSi3XO…` | `H9wlZ/tWgNp+Q4WQ5aUSi3XO…` | stable |
| `windows-11-arm` | *(leg crashed)* | `H9wlZ/tWgNp+Q4WQ5aUSi3XO…` | — |

Same platform, same SDK `10.0.400`, same commit, **different answer**. **Four** distinct `contentHash` values for one resolved version, and a single leg that is not self-consistent across runs.

The cause follows from the traced mechanism: whether a leg records the nuget.org hash or its SDK's bundled one depends on which source populated `~/.nuget/packages` first — a property of the runner image and its cache *at that moment*. The grouping accordingly follows **neither OS nor architecture** (`windows-2025` x64 and `windows-11-arm` arm64 agree; `ubuntu-24.04` x64 and `ubuntu-24.04-arm` arm64 do not).

**This is the strongest form of the answer.** A per-platform difference could at least be encoded in per-RID locks. A nondeterministic one cannot: widening `--locked-mode` would give a gate that fails **intermittently**, on a schedule nobody controls — worse than one that fails predictably, and precisely the "cross-platform flake" #17305 declined to create.

### Why a per-RID lock is the WRONG remedy

`packages.<rid>.lock.json` is for projects whose graph genuinely varies by `RuntimeIdentifier`. Nothing here declares one, and the grouping does not follow RID lines — two *different* architectures agree while two builds of the *same* OS disagree. Per-RID locks would encode a machine-state accident as a platform fact.

**The lever the SDK already provides** is the condition above: `<DisableImplicitLibraryPacksFolder>true</DisableImplicitLibraryPacksFolder>` removes the bundled folder as a source, so `FSharp.Core` resolves from nuget.org on every leg and one version means one `contentHash`. That changes restore behaviour and all 30 affected lock files, so it belongs in its own change — which **this lane is what would verify**. Deliberately not applied here: this PR measures.

## Finding 2 — every lock differs at byte level on Windows

`windows-2025` writes `packages.lock.json` with **CRLF**; the Unix legs write **LF** (measured directly on captured bytes). The 33 not already in Finding 1 report `differs-formatting-only` for that alone.

This one does **not** block `--locked-mode` — NuGet compares the resolved graph, not bytes — but it would make a "restore leaves the tree clean" check red on every Windows leg. Two different failure modes wanting two different remedies, which is precisely why the lane reports them as two verdicts instead of one "differs".

## The lane caught a defect in itself, on its first run

On the first run the `windows-11-arm` leg crashed in `dotnet --version` (exit `-2147483644`) — **transient; it restored cleanly on the second run** — and it **skipped both restore steps while still uploading a full 63-file manifest** — the files exactly as checked out. The first version of the comparison counted that as a fifth platform's opinion, and because a Windows checkout is CRLF it turned 33 genuinely-identical projects into `differs-formatting-only`. **A leg that did no work was voting** — the "a check that did not run looking like one that passed" class, inside the lane built to avoid it.

Fixed in `8ff4034a8d`: capture writes `restored`, computed from whether the restore steps actually succeeded; compare drops such a manifest *before* any comparison and fails the run for it. **Fail-closed** — an absent flag means `false`, so a manifest that does not vouch for its own restore is not trusted. It is reported separately from `missingPlatforms`, because "never reported" and "reported without doing the work" are different faults.

Run 2 confirms the wiring in CI — `restored=true` on all five legs, and the verdict is unchanged (`identical: 0 · differs-formatting-only: 33 · differs-unexplained: 30`). With a crashed leg present, it is now correctly excluded:
```
  macos-26:         arch=arm64 sdk=10.0.400 locks=63 restored=true
  ubuntu-24.04:     arch=x64   sdk=10.0.400 locks=63 restored=true
  ubuntu-24.04-arm: arch=arm64 sdk=10.0.400 locks=63 restored=true
  windows-2025:     arch=x64   sdk=10.0.400 locks=63 restored=true
  windows-11-arm:   arch=arm64 sdk=         locks=63 restored=false  <-- NOT COUNTED AS DATA
✗ leg did NOT restore, so its manifest is not data: windows-11-arm
  identical: 0 · differs-formatting-only: 33 · differs-unexplained: 30
```

## What would have to be true before widening

Finding 1 must be **fixed, not waived** — one resolved version must mean one `contentHash` on every leg. The edit it would then authorise is one step in `gate.yml`'s `build-and-test`: `Build (0 Warning(s) / 0 Error(s) required)`, from `dotnet build Zeta.sln -c Release` to `dotnet restore Zeta.sln --locked-mode` + `dotnet build Zeta.sln -c Release --no-restore`. Nothing else in the gate changes.
