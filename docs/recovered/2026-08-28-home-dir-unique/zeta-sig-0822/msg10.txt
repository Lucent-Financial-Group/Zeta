fix(forge-host): the token test wrote a credential into process.env — pass the environment in instead

`lint (bash retirement inventory + hygiene unit tests)` is red on `main`. The
ambient-credential-hoist guard reports five findings, all in one file:

    forge-host/github/check-observations.test.ts:291,295,303,306,309
    [process-env-assign-of-credential: assigns into process.env,
     which every child of this process inherits]

Arrived with #13964. Reproduced on clean `main` at `9f861ebef`: exit 1.

NOT A LINT TECHNICALITY. The two tests exercised `resolveGitHubToken()` by doing
`process.env["GH_TOKEN"] = "t1"` and restoring it in a `finally`. `process.env` is
inherited by every child the process spawns — including the real
`Bun.spawnSync(["gh", "auth", "token"])` inside the very function under test, and
any other test in the same run that shells out to `gh`. So for as long as the
assignment stood, real subprocesses were being handed a fake credential; and a
throw between the assignment and the `finally` leaves it standing for the rest of
the run. The guard was right.

THE FIX IS A SEAM, NOT A SUPPRESSION. `resolveGitHubToken` now takes the
environment as a parameter defaulting to `process.env`:

    export function resolveGitHubToken(
      env: Readonly<Record<string, string | undefined>> = process.env,
    ): string | null

Production behaviour is unchanged — every existing call site passes nothing and
reads the ambient environment exactly as before, which is what CI relies on.
Reading the environment was never the problem; writing a credential into it was.
The tests now pass `{ GH_TOKEN: "t1" }` and never touch `process.env` at all.

Also adds the `GITHUB_TOKEN` fallback test, which the file did not have — the
`??` in the resolver was previously covered on one side only.

OBSERVED, RECORDED, DELIBERATELY NOT FIXED. Writing that fallback test surfaced
that an EMPTY `GH_TOKEN` does not fall back to `GITHUB_TOKEN`: `??` only falls
through on null/undefined, so `""` is selected, the `!== ""` guard then rejects
it, and the function goes to `gh auth token` — skipping a `GITHUB_TOKEN` sitting
right there. Whether that is wrong depends on whether an empty `GH_TOKEN` means
"no token" or "unset", which is a call for whoever owns this resolver and is not
part of removing an ambient credential write. It is named in a comment at the
site and left alone. It is not asserted either way, because the branch it takes
ends in a real `gh` subprocess and that does not belong in the hermetic tier.
