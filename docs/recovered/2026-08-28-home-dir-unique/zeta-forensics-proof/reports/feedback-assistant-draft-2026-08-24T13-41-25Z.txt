TITLE
  Kernel panic: pmap_recycle_page 'page is referenced' @pmap_data.c under
  heavy concurrent VM activity (Mac Studio M2 Ultra, macOS 26.5.2)

AREA / TYPE
  macOS > Kernel  ·  Incorrect/Unexpected Behavior  ·  Reproducible sometimes

SUMMARY
  4 kernel panic(s) in a single day on one machine, all in the
  physical-map layer. The kernel attempts to recycle a physical page that
  still holds live references and fails its own invariant.

  3 of them share an IDENTICAL de-slid kernel backtrace, so this is a
  reproducible code path rather than independent memory faults.

WHAT IS RULED OUT (and why, from the reports themselves)
  - Third-party kernel code: 'roots installed: 0' with secure boot enabled.
  - Memory pressure: 'Compressor Info: 0% of compressed pages limit (OK) and
    0% of segments limit (OK) with 0 swapfiles and OK swap space'. 192 GB
    installed, ~97% free at the time of the panics.
  - Failing DRAM: the repeated panics land on the SAME instruction offsets
    across different KASLR bases, which random bit errors do not do.

STEPS TO REPRODUCE
  Not deterministically reproducible on demand. Observed conditions:
  1. Many Electron applications running concurrently, each with multiple
     renderer and GPU helper processes.
  2. Simultaneously, dozens of short-lived build/tool processes repeatedly
     mapping and unmapping large regions.
  3. Sustained load average well above core count (observed 64.91 at nine
     minutes of uptime) with no memory pressure.
  Panic occurs within hours under these conditions; four times in one day.
