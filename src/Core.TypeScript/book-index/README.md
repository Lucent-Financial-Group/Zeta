# The named index — person → everywhere they appear

A **derived** index into `docs/books/you-born-at-the-hinge/`, so a subject can be shown
**their whole footprint** rather than isolated passages, and so revision produces a **delta**
instead of a fresh interrogation.

> Aaron, on the consent design: *"this part we will need to have a back and forth on, based on
> their feedback and my many many revisions after talking about others, so a named index into
> the book would help — we should route and design that."*

## The problem this solves

Binding an approval to the **content hash of one passage** is correct, and it does not survive
contact with reality. Aaron revises many times *after* talking to the people involved, so
twenty subjects × five revisions is a hundred approval requests — and they will stop
answering. At that point the mechanism has trained everyone to ignore it, which is worse than
not having it.

Changing the **unit** fixes that, and it is better rather than merely cheaper:

1. **It answers the question a subject actually has** — *"what does this book say about me?"*
   No passage-level diff answers that.
2. **Consent becomes about portrayal, not sentences.** Someone can be comfortable with each
   individual line and not with the aggregate picture. Only the whole footprint surfaces that.
3. **Revision churn gets scoped.** Revise one section and only the people indexed there need to
   look — at a delta, not at the whole thing again.

`CONSENT-LEDGER.md` remains the source of truth for what anyone agreed to. Nothing here grants,
widens, or discharges any consent.

## The thing that decides whether this works: the index is DERIVED

A hand-kept index drifts, and a drifted index means someone **approved coverage that no longer
reflects the text** — coverage that looks complete and is not, landing on a named third party
rather than on CI.

So the index is generated by **scanning the prose** on every run. The only hand-maintained
artifact is `SUBJECTS.json`: **who the people are and what state their consent is in**, which
is the one thing no scan can derive.

### Where the failure mode actually moves to

The obvious design is in-text markers plus an audit that catches *"a person appears in prose
with no marker."* Scanning is strictly **more** derived than that — there is no marker to
forget. But the under-report class does not vanish; it **relocates**:

> With a derived index there is exactly one way to under-report: **a person is in the prose and
> the registry does not know they exist.**

That is what `sweep.ts` hunts, and it is why **the sweep, not the index, is the load-bearing
artifact.**

## Files

| Path | Kind | What it is |
|---|---|---|
| `docs/books/…/SUBJECTS.json` | **hand-maintained** | Who the subjects are, their consent state, their detector strings. The only hand-kept part, deliberately the smallest. |
| `docs/books/…/SUBJECT-INDEX.md` / `.json` | generated | The index. Locations and hashes — **never prose**. |
| `docs/books/…/SUBJECT-SWEEP-BASELINE.json` | ratchet | Capitalised tokens present when the sweep landed. **Not** an allowlist. |
| `docs/books/…/SUBJECT-INDEX-ADJUDICATIONS.json` | human calls | Hash-keyed "this string match is not an appearance". Expires when the text changes. |
| `registry.ts` · `scan.ts` · `sweep.ts` | library | Parsing, derivation, the sweep. |
| `build-index.ts` | CLI | Generates the index; `--footprint <id>` prints what you send a person. |
| `audit-coverage.ts` | CLI | **The falsifier.** Five checks, three exit codes. |
| `delta.ts` | CLI | *"Here is what changed about you since you approved."* |

## Running it

```bash
bun src/Core.TypeScript/book-index/build-index.ts            # regenerate the index
bun src/Core.TypeScript/book-index/build-index.ts --footprint max > max-footprint.md
bun src/Core.TypeScript/book-index/audit-coverage.ts         # the audit (default: repo-wide leak scope)
bun src/Core.TypeScript/book-index/audit-coverage.ts --leak-scope book   # fast, narrower
bun src/Core.TypeScript/book-index/delta.ts --approvals <file>
```

**Exit codes, and the distinction is the point:**

| code | meaning |
|---|---|
| `0` | every check **ran** and passed |
| `1` | a check ran and **failed** |
| `2` | a check **could not run** — *not* a pass |

`--allow-unchecked` downgrades a `2` so the other checks can block, and still refuses a clean
`0` while anything went unchecked. The unchecked count sits beside the failure count in the
summary line, because *"0 failures"* while three checks never ran is a green board that means
nothing.

## Names that are not ours to write

`Lucent-Financial-Group/Zeta` is a **public** repository, so writing a name into `SUBJECTS.json`
publishes it. The registry therefore **never introduces a name the ledger has not already
established as consented-and-named**. Every other subject carries
`nameWithheldFromRegistry: true`, and its name strings come from a **local overlay that is
never committed**:

```jsonc
// ~/.claude/projects/<slug>/memory/book-subjects-local.json
// or wherever $ZETA_BOOK_SUBJECTS_LOCAL points
{ "names": { "late-sister": ["…"], "holly-hill-subject": ["…", "…"] } }
```

Without the overlay the leak check **cannot run**, and that is reported as `UNCHECKED` with
exit `2` — never as a pass. That is the fail-closed half: `withheldNamesFor` returns `null`
("could not check"), which is a different value from `[]` ("checked, found nothing"), and a
test pins the difference.

The audit's report **never echoes a withheld name**. It prints the subject id and the paths, so
the report can be pasted anywhere without republishing exactly what the check protects.

## The four states (five, and two pairs enforce identically)

| state | name may appear | may appear at all |
|---|---|---|
| `named` | yes | yes |
| `role-only` | no | yes |
| `pending` | no | yes |
| `revoked` | no | no |
| `omitted` | no | no |

`pending` and `role-only` **enforce identically**; so do `revoked` and `omitted`. They are kept
apart because the **disposition** differs — `pending` generates a follow-up (someone was asked
and has not answered), `role-only` is settled; `revoked` is a withdrawal, `omitted` is a
protection that was never in question. Pretending they enforce differently would be fake
precision, so the identity of the enforcement halves is **checked by a test**, not asserted in
prose.

The live precedent for `pending` is on file: a subject asked 2026-08-25, carried **role-only
until she answers**. `role-only` is a *content* constraint, not a flag — the leak check is what
makes it real.

### What the states cannot express, said plainly

One ledger row is **scoped**: personal-relation naming permitted, professional attribution
denied. No state expresses that, so the registry enforces the **stricter half** (no name) and
records the rest in a free-text `scopeNote` that **nothing enforces**. Saying so is the point —
a scoped constraint that *looks* enforced and is not would be worse than one that is visibly a
human's job.

## The sweep is a ratchet, not an allowlist

A capitalised-token sweep over 129k words finds ~217 candidates, nearly all cited authors,
places, products and vocabulary. Hand-listing those as "fine" would recreate exactly the
drift-prone surface this design exists to avoid — and a future agent could turn the check green
by appending to it.

So:

- a candidate **not in the baseline is a FAILURE** — a new person entering the prose without a
  registry row goes red on the commit that adds them;
- a baseline entry **no longer in the prose is STALE** and must be pruned, so the baseline
  cannot accumulate dead cover;
- entries default to `triaged: false`. **The untriaged count is debt**, printed on every run,
  and it can only go down.

Mechanical exclusions only — ALL-CAPS acronyms, internal-hump identifiers, inline code, link
targets, calendar words, registered detectors, tokens ever seen lowercase, and tokens that only
ever appear sentence-initially. Every one is derivable from the markdown; none is a judgement
about a particular word.

## Adjudications expire

Five blocks in this book say *"his son is omitted entirely"* — editorial notes **about** the
omission, which a string match cannot tell from a mention of him. Those need a human's one-line
call, recorded in `SUBJECT-INDEX-ADJUDICATIONS.json`.

Keying on the **block hash** rather than a file and line is what stops it becoming a permanent
exemption: **edit the text and the adjudication expires**, because the hash it was granted
against no longer exists — and a stale adjudication is itself a failure, so the file cannot
quietly accumulate cover. Same shape as the repo's `b-ref-adjudicated` annotations: checked,
not trusted.

## How it meets the consent mechanism

Consent binds to a subject's **`entryHash`** — the fingerprint of their whole footprint — not to
a per-passage hash.

- `entryHash` unchanged → **the approval still holds. Nobody is asked anything.**
- `entryHash` changed → a delta **for that subject only**: added, removed, revised.

Canonicalisation is the deliberate half: whitespace runs collapse and markers are stripped, so
a **reflow does not invalidate an approval** — consent here is about portrayal, and rewrapping
a paragraph does not change how someone is portrayed. Wording, emphasis and punctuation are all
*inside* the hash, because each can change a portrayal.

### Coordination — the proposed schema, and where it may disagree

`ApprovalRecord` in `delta.ts` is the interface with the **GitHub-review consent mechanism and
its verifier**, which is owned by another agent and was not landed at the time of writing:

```jsonc
{
  "book": "you-born-at-the-hinge",
  "approvals": [{
    "subjectId": "max",
    "entryHash": "sha256:…",      // the binding value
    "approvedAt": "2026-08-26",
    "approvedVia": "…",            // the verifier's territory, opaque here
    "passages": [{ "file": "…", "hash": "sha256:…" }]   // so a delta can say WHICH parts changed
  }]
}
```

**The division of labour:** the verifier owns *how an approval is obtained and recorded*; this
index owns *what an approval is bound to*.

**Two places the designs could genuinely disagree**, stated rather than silently reconciled:

1. **The binding unit.** If the verifier binds per passage, that is the design this index was
   built to replace, and the disagreement is substantive rather than cosmetic — one of the two
   has to move, and it should be settled between them, not by either inventing a second schema.
2. **Canonicalisation.** If the verifier hashes raw bytes, a reflow will invalidate approvals
   here and not there (or the reverse), and the two will disagree about whether anything
   changed. Whichever rule wins, **both sides must use the same one.**

## Honest limits

- **A person described identifiably but never named is invisible to the scan.** *"My old boss
  at the meter company, the one who ran the simulator"* has no registered string in it. Two
  partial answers ship — registered **role phrases** widen recall beyond names, and an optional
  **in-text marker** lets a human declare an appearance the scan cannot see — and **neither is
  a fix.** The residual gap is real, **unmeasured**, and a human's job. It is the reason the
  index says what it can see and never claims completeness.
- **The scoped-consent gap** above: `scopeNote` is enforced by nobody.
- **`--leak-scope repo`** takes ~30s (one `git grep` pass) and covers tracked files only.
- **Not wired into CI**, deliberately: the leak check needs a local overlay of names that must
  never be in the repository, so a CI runner cannot perform it. A human runs this.
- **Register:** the mechanism (derivation, hashing, ratchet, expiry) is `metered` — every claim
  above has a test that fails without it, and the two load-bearing guards were mutation-checked.
  The `REVISION_SIMILARITY_THRESHOLD = 0.6` rewrite pairing is `unmetered` and **display only**;
  it never affects a verdict. The claim that the sweep *finds every unregistered person* is
  **false and not made** — see the first bullet.
