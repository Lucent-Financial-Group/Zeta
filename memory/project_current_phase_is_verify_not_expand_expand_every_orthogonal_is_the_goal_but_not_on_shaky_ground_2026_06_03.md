**The two phases + the gate between them:**

- **VERIFY (now)** — prove the foundation: prove the small root-axiom basis,
  prove the primitives (4-oracle byte-lock + homeostat-proven-from-seed), connect
  them as layered lemmas, close the asserted-in-prose → proven gap. This is the
  current operating mode.
- **EXPAND (the goal)** — *expand every orthogonal*: grow code outward from the
  verified seed across each orthogonal dimension (the seed-first / grow-from-seed
  direction; the root dimensions as the orthogonal basis). This is the
  destination, not the current stage.

**Why verify-before-expand (the gate):** orthogonal expansion *multiplies*
whatever it's built on. Expanding across N orthogonals on an unproven foundation
multiplies the shakiness N ways — *"that won't work on shaky ground."* So the
foundation must be proven (homeostat-from-seed) *before* the orthogonal expansion,
or the expansion compounds unverified ground instead of proven ground.

**Where it sits in the engine lifecycle:** the verify-gate is exactly between
*razor compresses* (to the canonical seed) and *Otto's expansion expands* (the
seed outward) — razor → **[VERIFY]** → expand → Ace distributes → Zeta runs →
Agora breathes life. We are at the VERIFY gate, not yet through it.

**Operational implication (current disposition):**
- Default to verification / proof-canonicalization / consolidation work, NOT
  new-primitive-building or orthogonal expansion.
- A fresh session should NOT default to expand-mode — check the phase first.
  Building new orthogonal surface before the basis is proven is building on shaky
  ground.
- This session's shape (proof rules, multi-tower §8, gate-reach-boundary,
  steward maintenance) IS verify-stage work — correct for the phase.
- The phase is project-STATE: it flips to EXPAND when the foundation is proven
  (when the basis + primitives clear the homeostat-proven-from-seed bar). Update
  this memory at the transition.
