# byte-lock receipts pin third-party versions no other oracle can witness

## Origin

Aaron, 2026-09-12, on re-recording the MiniGrid carrier for a numpy patch bump:

> *"i don't like having 3rd party libaries needing to be the same across languages for our
> byte lock agreements, what happens when we want to use something other in numpy in another
> oracle?"*

## The measurement

The MiniGrid Empty-5x5 receipt is byte-locked across the Python and F# oracles: both must
produce identical bytes. But its fields divide into two kinds, and only one of them is an
agreement.

**INDEPENDENTLY COMPUTED — the lock is real here.** `MiniGridEmpty5x5Adapter.fs` genuinely
simulates the grid: it carries `directionDelta`, initial and goal positions, and the forward
transition, and derives the trajectory itself. So positions, directions, reward bits, the
reset-observation digest and the upstream commit are produced TWICE by two implementations.
Byte-equality there is exactly the independent-redundancy evidence the four-oracle discipline
exists to buy.

**TRANSCRIBED — the lock is vacuous here.** `fixtureRuntime` (python, minigrid, gymnasium,
numpy, pygameCe) is read straight out of the carrier and re-emitted:

```fsharp
FixtureNumPy = readString fixtureRuntime "numpy"
```

F# does not run numpy and cannot observe its version. Byte-equality on that field proves only
that both oracles opened the same file. The repository already names this shape, in
`.claude/rules/maintenance-commit-on-another-agents-branch-carries-no-block.md`: *"the parser
cannot distinguish a copied attestation from an earned one."* Same defect, different artifact.

## Why it does not generalise, which is the sharper half

A third oracle is the test. A Rust adapter would use `ndarray`; a TypeScript one something
else again. There is no honest shared `fixtureRuntime` across them — a new oracle could only
TRANSCRIBE Python's numpy version, which is meaningless for it and which it cannot check. The
field cannot generalise, so a byte-lock containing it cannot either. The lock is therefore
capped at two oracles by a field that contributes nothing to what the lock proves.

## The cost is already paid, and measured

Re-recording for a numpy PATCH bump (2.5.1 -> 2.5.3) touched **five artifacts and two
independently-pinned fingerprints**:

| # | artifact | why it moved |
|---|---|---|
| 1 | carrier `fixtureRuntime.numpy` | the recorded runtime |
| 2 | `CARRIER_FINGERPRINT` (Python) | pins the carrier's bytes |
| 3 | `CarrierFingerprint` (F#) | the F# oracle pins it INDEPENDENTLY |
| 4 | python receipt | regenerated by replay |
| 5 | fsharp receipt | byte-identical to (4) |

Both test suites had to run. **None of that work said anything about whether the two
implementations agree** — the trajectory was bit-identical throughout (steps, seeds, digest
and upstream commit all unchanged; `numpy` was the only differing field).

Worse, it creates standing pressure NOT to update dependencies, since every patch bump is a
cross-oracle event. That is a security cost paid to protect a field that proves nothing.

## The shape that fixes it

Split the receipt by WHO CAN WITNESS WHAT.

| region | contents | byte-locked across oracles? |
|---|---|---|
| **invariant** | environmentId, stateProjection, maxSteps, seeds, steps, positions, reward bits, digests, upstreamCommit, source-file hashes | **yes** — every oracle derives these |
| **provenance** | python / minigrid / gymnasium / numpy / pygame-ce | **no** — only the Python oracle can witness it |

The carrier needs the same split: F# pins the carrier's WHOLE bytes today, which is precisely
why a numpy bump breaks the F# oracle. Provenance must sit outside the region any oracle other
than Python hashes.

**Keep recording provenance.** It is what tells you WHAT MOVED if the trajectory ever does
change, and that is worth having. The claim here is only that it must not be byte-locked
ACROSS oracles — record it, hash it on the Python side, and leave it out of the shared bytes.

## Falsifier

The test that proves this fixed, and which cannot pass today:

> Change a Python-only dependency version. The cross-oracle receipt bytes must NOT change, and
> the F# oracle must NOT need recompiling or re-pinning.

A second, stronger one for the generalisation claim: add a stub third oracle that declares a
DIFFERENT numeric library and have it produce the invariant region. It must reach byte-equality
with the other two without ever naming numpy.
